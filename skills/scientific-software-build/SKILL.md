# 科学软件构建与运行验证

组织可重复的软件构建，明确源代码、编译工具链与实际可运行能力。仅声明已经检查过的版本和组件支持。

## 工作流程

1. 确认软件、版本、目标功能、硬件架构和可用源码。商业或受许可限制的源码由合法可用来源提供，不把源码、许可文件或授权信息打包进技能。
2. 只读探测编译器、MPI 包装器、GPU 工具链、数学库及现有安装。登录节点看不到 GPU 不代表计算节点没有 GPU。
3. 为新版本或补丁版本建立独立构建树；保留已验证的原版。区分源码目录、构建目录、安装前缀和计算目录。
4. 按目标版本说明选择配置，核对头文件、链接库与运行库的一致性。不要仅以编译器版本推断架构兼容性。
5. 在适合的资源上构建。需要计算节点时先准备作业，提交另依当前授权；避免把大型编译或运行验证放在受限登录节点。
6. 分层记录源码准备、编译、链接和运行验证结果。检查动态依赖，并在目标架构上用小型实际算例检验所需功能。
7. 保存配置、构建命令和运行验证记录。未经目标架构验证的二进制标为未验证，不仅凭文件存在宣称安装成功。

## 按需参考

- VASP、MPI、GPU 与补丁变体：读取 [构建适配](references/builds.md)。
- 有实际性能疑问时：读取 [受控性能测试](references/benchmarking.md)。

## 输出

构建配置、独立安装或构建目录、环境加载脚本及 build-report.json。可记录软件版本与源码校验信息；不在启动脚本中添加校验和阻断门槛。

## 使用约定

- 依赖路径、环境名称、调度资源和科学参数从当前请求、项目文件或运行配置获取；只读探测缺失的环境信息，关键科学选择不明确时再询问。
- 保留源数据与既有结果，使用新的输出位置；提交、取消作业或破坏性操作须在当前授权范围内进行。准备输入本身不等于授权提交。
- 生成的脚本采用顶部配置、清楚的输入输出和相对资源引用。当前运行的本机路径可以记录在运行产物中，不回写到可分享的技能文件。
